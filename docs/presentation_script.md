**【講稿】**
這是一個在地二手物交易平台，技術架構採用 Vue.js 前端搭配 Supabase 後端服務。

### 投影片 6: 測試設計方法
**【講稿】**
高覆蓋率不是靠隨便寫寫，我們運用了課程教的四種測試設計方法：
1.  **等價類別劃分**：減少冗餘測試，比如評分系統。
2.  **邊界值分析 (BVA)**：我們採用更嚴謹的 **3-value BVA**，測試邊界本身與左右鄰居。
3.  **狀態轉換測試**：這是最難的部分，專門用來測交易流程，確保不能從「已完成」跳回「取消」。
4.  **錯誤猜測**：憑經驗去測那些容易爆掉的地方，比如網路斷線。

### 投影片 9: 狀態轉換測試 - 依 API 重要性排序

#### ★★★★★ 交易狀態流轉 (`transaction_before_meetAPI.test.js`, `transaction_meetAPI.test.js`)
```
┌──────────┐   initiateTransaction   ┌────────────┐
│  (初始)  │ ───────────────────────► │ confirming │
└──────────┘                          └────────────┘
                                            │
                    ┌───────────────────────┼───────────────────────┐
                    │                       │                       │
            buyerConfirmTransaction    cancelTransaction      (自動超時)
                    │                       │                       │
                    ▼                       ▼                       ▼
             ┌───────────┐           ┌────────────┐          ┌────────────┐
             │  pending  │           │ cancelled  │          │  expired   │
             └───────────┘           └────────────┘          └────────────┘
                    │
        finalizeTransactionWithCode
                    │
                    ▼
             ┌───────────┐
             │ completed │
             └───────────┘
```

| 狀態轉換 | 觸發函式 | 測試檔案 |
|----------|----------|----------|
| 初始 → confirming | `initiateTransaction()` | `transaction_before_meetAPI.test.js` |
| confirming → pending | `buyerConfirmTransaction()` | `transaction_before_meetAPI.test.js` |
| confirming → cancelled | `cancelTransaction()` | `transaction_before_meetAPI.test.js` |
| pending → completed | `finalizeTransactionWithCode()` | `transaction_meetAPI.test.js` |

#### ★★★★☆ 徽章獲取狀態 (`badgesAPI.test.js`)
| 狀態 | 進度 | 描述 |
|------|------|------|
| in_progress | 0-99% | 正在累積進度 |
| earned | 100% | 已獲得徽章 |

#### ★★★★☆ 議價狀態轉換 (`transactionsAPI.test.js`)
| 狀態轉換 | 函式 | 說明 |
|----------|------|------|
| pending → accepted | `respondToOffer('accept')` | 接受報價 |
| pending → declined | `respondToOffer('decline')` | 拒絕報價 |
| pending → countered | `respondToOffer('counter', 金額)` | 還價 |

**【講稿】**
這張圖是我們的交易狀態機。系統規定交易只能從 Pending -> Confirming -> Completed。
我們的測試重點不僅是「走通」這條路，更重要的是「擋住」不該走的路，例如有人想把「已完成」的訂單「取消」，測試程式必須報錯。這確保了交易邏輯的安全性。

### 投影片 15: 結論與心得
**【講稿】**
做完這個專題，我們最大的體悟，其實來自於**沒有即時導入 TDD 的痛苦**。
因為專案啟動時，我們是「先寫程式、最後才補測試」。這導致了幾個嚴重的問題：
1.  **程式碼龐大難測**：回頭補測試時，發現很多函式寫得太複雜，難以拆解。
2.  **責任歸屬不清**：多人協作下，後寫測試的人常分不清這是誰寫的 Bug。
3.  **修復成本高昂**：往往為了補一個測試覆蓋率，這才發現邏輯有漏洞，得重構整段程式碼。
如果能重來，我們一定會堅持先寫測試 (Test-First)。

## 🛡️ 教授 QA 攻防 (Defense Cheat Sheet)

**Q1: 你們說沒有做 TDD，那怎麼保證測試品質？/ 沒做 TDD 的主要困難是什麼？**
*   **答**：這確實是我們這次最大的教訓。沒有 TDD，我們面臨了「**先射箭再畫靶**」的困境。
    *   **困難點**：因為程式碼已經寫死且耦合度高，我們為了讓測試通過，必須花大量時間去 Mock 複雜的依賴，甚至被迫重構原本「可以動」的程式碼來讓它「可被測試」。
    *   **品質保證**：雖然過程痛苦，但我們最終堅持所有 API 的 Branch Coverage 都要達標，這強迫我們回頭審視邏輯，最終還是抓出了 12 個隱藏 Bug。

**Q2: 為什麼只測 API 層？前端 UI 沒測嗎？**
*   **答**：依據「測試金字塔」原則，單元測試應該最多且最底層。UI 變動頻繁，維護成本高。我們選擇鎖定不變的「商業邏輯」(API)，這樣投資報酬率 (ROI) 最高。且我們的 API 包含所有後端交互邏輯，測 API 等於測了系統核心。

**Q3: 這些測試資料 (Mock Data) 是寫死的嗎？這樣準嗎？**
*   **答**：我們使用了 **Stub/Mock** 技術。我們 Mock 了 Supabase 的外部連線，這是單元測試的標準作法，目的是隔離外部依賴，讓測試跑得快且穩定 (Deterministic)。如果要測真實資料庫，那是「整合測試」的範疇，我們專案書面報告中有提到這屬於未來規劃。

**Q4: 複雜度 2633 是怎麼算出來的？**
*   **答**：我們參考了 McCabe Cyclomatic Complexity (圈複雜度) 的算法。我們寫了一個 script 解析所有 JS 檔案，計算 `if`、`for`、`while` 等分支關鍵字的數量並加總。

**Q5: 3-value BVA 跟 2-value 差在哪？**
*   **答**：差在更嚴謹。2-value 只測邊界值本身，3-value 多測了「鄰居」。例如大於 5 分，2-value 可能只測 5 和 6；3-value 我們會測 5, 6, 甚至 4，確保邊界兩側的行為都符合預期，避免 Off-by-one error (差一錯誤)。
