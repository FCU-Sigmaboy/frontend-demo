# 投影片 6: 測試設計方法

## 四種測試設計技術

### 1️⃣ 等價類別劃分 (Equivalence Partitioning)

> 💡 把輸入分組，每組只測一個代表值

> _ISTQB® CTFL v4.0, Section 4.2.1_

- 有效等價類：評分 1-5
- 無效等價類：評分 < 1 或 > 5

### 2️⃣ 邊界值分析 (3-value BVA)

> 💡 專測「臨界點」，Bug 最常發生在邊界

> _ISTQB® CTFL v4.0, Section 4.2.2_

| 邊界          | 測試值                         |
| ------------- | ------------------------------ |
| Bronze/Silver | 998, **999**, **1000**, 1001   |
| Silver/Gold   | 4998, **4999**, **5000**, 5001 |

### 3️⃣ 狀態轉換測試 (State Transition)

> 💡 驗證狀態流程正確，並測試「禁止轉換」被拒絕

> _ISTQB® CTFL v4.0, Section 4.2.4_

```
┌─────────┐       ┌───────────┐       ┌────────────┐
│  IDLE   │ ────► │  PENDING  │ ────► │ CONFIRMING │
└─────────┘       └─────┬─────┘       └──────┬─────┘
                        │                    │
                        ▼                    ▼
                  ┌────────────┐       ┌────────────┐
                  │ CANCELLED  │       │ COMPLETED  │ ──✕──► CANCELLED
                  └────────────┘       └────────────┘    (無效轉換)
```

### 4️⃣ 錯誤猜測 (Error Guessing)

> 💡 憑經驗預測哪裡會出錯，針對性測試

> _ISTQB® CTFL v4.0, Section 4.4.2_

- 網路錯誤 / 401 未授權 / 500 伺服器錯誤
- RPC 返回 `null` 或空陣列

# 投影片 7: 測試案例範例

## 等價類別測試範例

```javascript
describe("評分驗證測試", () => {
  // 有效等價類別
  it("評分 1 應該被接受 (最小有效值)", () => {
    expect(validateRating(1)).toBe(true);
  });

  it("評分 5 應該被接受 (最大有效值)", () => {
    expect(validateRating(5)).toBe(true);
  });

  // 無效等價類別
  it("評分 0 應該被拒絕 (低於最小值)", () => {
    expect(validateRating(0)).toBe(false);
  });

  it("評分 6 應該被拒絕 (超過最大值)", () => {
    expect(validateRating(6)).toBe(false);
  });
});
```

# 投影片 9: 狀態轉換測試

## 交易狀態流程圖

```
    ┌──────────┐      發起交易      ┌─────────────┐
    │  (無)    │ ─────────────────► │   pending   │
    └──────────┘                    └─────────────┘
                                          │
                          ┌───────────────┴───────────────┐
                          ▼                               ▼
                    ┌─────────────┐                 ┌─────────────┐
                    │  cancelled  │                 │ confirming  │
                    └─────────────┘                 └─────────────┘
                                                          │
                                                          ▼
                                                    ┌─────────────┐
                                                    │  completed  │
                                                    └─────────────┘
```

## 狀態轉換測試案例

- ✅ pending → confirming (買家確認)
- ✅ confirming → completed (確認碼驗證)
- ✅ pending → cancelled (取消交易)
- ❌ completed → cancelled (無效轉換)

# 投影片 15: 結論與心得

## 主要成果

- ✅ 完成 **760 個**單元測試
- ✅ API 層覆蓋率達 **90%** (語句)
- ✅ 建立完整的測試基礎設施
- ✅ 自動化報告生成

## 學習心得

### 1️⃣ 測試驅動開發的重要性

- 先寫測試再寫程式碼能確保功能正確性

### 2️⃣ 覆蓋率不等於測試品質

- 高覆蓋率不代表測試完整
- 邊界值和錯誤處理更重要

### 3️⃣ Mock 策略的設計

- 統一的 Mock 設置能減少重複程式碼

### 4️⃣ API 層測試的價值

- API 是業務邏輯的核心
