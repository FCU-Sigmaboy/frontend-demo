# 三、測試設計

## 3.1 等價類別劃分 (Equivalence Partitioning)

> **簡單說**：把輸入資料分組，每組只測一個代表值，節省測試時間。

> **ISTQB® 定義**：將輸入資料劃分為群組，同一分區內的所有元素預期會以相同方式被系統處理。若分區內某測試案例有效，則該分區內所有測試案例都應有效。
>
> _ISTQB® CTFL Syllabus v4.0, Section 4.2.1_

### 範例：評分驗證測試

**等價類別定義：**

- 有效等價類：評分 1-5
- 無效等價類：評分 < 1 或 > 5

```javascript
// tests/unit/api/create_review.test.js

describe('評分等價類別測試', () => {
  // 有效等價類別
  describe('有效評分範圍 (1-5)', () => {
    it('評分 1 應該被接受', async () => {
      const result = await createReview({ rating: 1, ... })
      expect(result.success).toBe(true)
    })

    it('評分 3 應該被接受', async () => {
      const result = await createReview({ rating: 3, ... })
      expect(result.success).toBe(true)
    })

    it('評分 5 應該被接受', async () => {
      const result = await createReview({ rating: 5, ... })
      expect(result.success).toBe(true)
    })
  })

  // 無效等價類別
  describe('無效評分範圍', () => {
    it('評分 0 應該被拒絕', async () => {
      const result = await createReview({ rating: 0, ... })
      expect(result.error).toBeDefined()
    })

    it('評分 6 應該被拒絕', async () => {
      const result = await createReview({ rating: 6, ... })
      expect(result.error).toBeDefined()
    })

    it('評分 -1 應該被拒絕', async () => {
      const result = await createReview({ rating: -1, ... })
      expect(result.error).toBeDefined()
    })
  })
})
```

## 3.2 邊界值分析 (Boundary Value Analysis)

> **簡單說**：專測「臨界點」，因為 Bug 最常發生在邊界值。

> **ISTQB® 定義**：邊界值分析是一種基於等價分區邊界進行測試的技術。ISTQB 定義兩種變體：
>
> - **2-value BVA**：測試邊界值及其最接近的鄰居
> - **3-value BVA**：測試邊界值及其兩側的鄰居（更嚴謹）
>
> _ISTQB® CTFL Syllabus v4.0, Section 4.2.2_

**本專案採用 3-value BVA**

### 範例：點數等級邊界測試

| 等級     | 點數範圍  | 邊界測試值 (3-value)                          |
| -------- | --------- | --------------------------------------------- |
| Bronze   | 0-999     | 0, **998**, **999**, **1000**, 1001           |
| Silver   | 1000-4999 | **999**, **1000**, 4998, **4999**, **5000**   |
| Gold     | 5000-9999 | **4999**, **5000**, 9998, **9999**, **10000** |
| Platinum | 10000+    | **9999**, **10000**, 10001                    |

```javascript
// tests/unit/api/pointsAPI.test.js

describe("等級邊界值測試", () => {
  describe("Bronze 等級邊界", () => {
    it("0 點應該是 Bronze", () => {
      expect(getLevelTier(0)).toBe("bronze");
    });
    it("999 點應該是 Bronze", () => {
      expect(getLevelTier(999)).toBe("bronze");
    });
    it("1000 點應該是 Silver (邊界跨越)", () => {
      expect(getLevelTier(1000)).toBe("silver");
    });
  });

  describe("Silver/Gold 邊界", () => {
    it("4999 點應該是 Silver", () => {
      expect(getLevelTier(4999)).toBe("silver");
    });
    it("5000 點應該是 Gold (邊界跨越)", () => {
      expect(getLevelTier(5000)).toBe("gold");
    });
  });

  describe("Gold/Platinum 邊界", () => {
    it("9999 點應該是 Gold", () => {
      expect(getLevelTier(9999)).toBe("gold");
    });
    it("10000 點應該是 Platinum (邊界跨越)", () => {
      expect(getLevelTier(10000)).toBe("platinum");
    });
  });
});
```

## 3.3 狀態轉換測試 (State Transition Testing)

> **簡單說**：驗證系統狀態流程是否正確，並測試「禁止的轉換」是否被正確拒絕。

> **ISTQB® 定義**：狀態轉換測試用於測試系統在不同狀態之間的轉換。測試案例設計應涵蓋：
>
> - 典型狀態序列
> - 所有有效轉換 (0-switch coverage)
> - **無效轉換**（預期應被拒絕）
>
> _ISTQB® CTFL Syllabus v4.0, Section 4.2.4_

### 交易狀態流程圖

```
                    ┌─────────────────────────────────────────────┐
                    │              交易狀態轉換圖                 │
                    └─────────────────────────────────────────────┘

    ┌──────────┐      發起交易      ┌─────────────┐     買家確認    ┌─────────────┐
    │  (無)    │ ─────────────────► │   pending   │ ──────────────► │ confirming  │
    └──────────┘                    └─────────────┘                 └─────────────┘
                                          │                               │
                                          │ 取消                          │ 確認碼驗證
                                          ▼                               ▼
                                    ┌─────────────┐                 ┌─────────────┐
                                    │  cancelled  │ ◄────────────── │  completed  │
                                    └─────────────┘      取消       └─────────────┘
```

```javascript
// tests/unit/api/transactionsAPI.test.js

describe("交易狀態轉換測試", () => {
  describe("有效狀態轉換", () => {
    it("pending → confirming (買家確認)", async () => {
      const transaction = { status: "pending" };
      const result = await buyerConfirmTransaction(transaction.id);
      expect(result.data.status).toBe("confirming");
    });

    it("confirming → completed (確認碼驗證)", async () => {
      const transaction = { status: "confirming" };
      const result = await finalizeTransactionWithCode(
        transaction.id,
        "123456",
      );
      expect(result.data.status).toBe("completed");
    });

    it("pending → cancelled (取消交易)", async () => {
      const transaction = { status: "pending" };
      const result = await cancelTransaction(transaction.id, "reason");
      expect(result.data.status).toBe("cancelled");
    });
  });

  describe("無效狀態轉換", () => {
    it("completed → cancelled 應該失敗", async () => {
      const transaction = { status: "completed" };
      const result = await cancelTransaction(transaction.id, "reason");
      expect(result.error).toBeDefined();
    });

    it("cancelled → confirming 應該失敗", async () => {
      const transaction = { status: "cancelled" };
      const result = await buyerConfirmTransaction(transaction.id);
      expect(result.error).toBeDefined();
    });
  });
});
```

## 3.5 錯誤猜測 (Error Guessing)

> **簡單說**：憑經驗預測哪裡會出錯（如網路斷線、空值輸入），並針對這些場景設計測試。

> **ISTQB® 定義**：錯誤猜測是一種依賴測試人員知識、經驗和直覺來識別可能包含缺陷區域的技術。
>
> _ISTQB® CTFL Syllabus v4.0, Section 4.4.2_

### 常見錯誤場景測試

| 錯誤場景                 | 模擬方法                                                 | 預期行為                 | 覆蓋模組                |
| :----------------------- | :------------------------------------------------------- | :----------------------- | :---------------------- |
| 網路斷線                 | `vi.mock` 返回 `{ error: { message: 'Network Error' } }` | 拋出「網路連線失敗」錯誤 | 所有 API 模組           |
| 未授權 (401)             | `vi.mock` 返回 `{ error: { code: 401 } }`                | 拋出「授權失敗」錯誤     | `location.js`           |
| 資料庫錯誤 (500)         | `vi.mock` 返回 `{ error: { code: 500 } }`                | 拋出「伺服器錯誤」提示   | 所有 API 模組           |
| RPC 返回 `null` 或空陣列 | `vi.mock` 返回 `{ data: null }` / `{ data: [] }`         | 正確處理 Fallback 邏輯   | `ragQaAPI.js`           |
| 空字串 / 特殊字元輸入    | 傳入 `""`, `null`, `undefined`, SQL 注入字串             | 輸入驗證並拒絕           | `get_searchItemsAPI.js` |

## 6.2 Bug 詳細說明

### Bug #1: 點數格式化負數顯示錯誤

**問題描述：** 當點數為負數時，格式化函數顯示錯誤。

**發現方法：** 邊界值測試

**修復方式：**

```javascript
// Before (錯誤)
function formatPoints(points) {
  return points.toLocaleString();
}

// After (正確)
function formatPoints(points) {
  const absPoints = Math.abs(points);
  const formatted = absPoints.toLocaleString();
  return points < 0 ? `-${formatted}` : formatted;
}
```

### Bug #3: 評分驗證範圍錯誤

**問題描述：** 評分允許 0 分，應該只允許 1-5 分。

**發現方法：** 等價類別測試

**修復方式：**

```javascript
// Before (錯誤)
if (rating < 0 || rating > 5) {
  return { error: "評分必須在 0-5 之間" };
}

// After (正確)
if (rating < 1 || rating > 5) {
  return { error: "評分必須在 1-5 之間" };
}
```

## 7.3 心得
    
### 測試開發心得
    
本專案啟動時，並未協同測試並行開發，導致回頭進行測試工作時，膨脹的專案令複雜度大為提高，並且難以劃分開發者的責任歸屬。
    
1. **TDD 的價值**
   - 先寫測試再寫程式碼能確保功能正確性
    
2. **覆蓋率迷思**
   - 高覆蓋率不等於高品質，邊界值與錯誤處理更重要
    
3. **Mock 策略**
   - 統一的 Mock 設定能減少重複程式碼並隔離外部相依性
    
4. **API 測試價值**
   - API 是業務邏輯核心，完整測試確保系統穩定
